# 08 核查说明（Ghidra 与 IDA 差异）

> 针对你提到的「Ghidra 结果与 IDA 冲突、最终 IDA 正确」问题，本报告说明本次逆向的**方法与可靠性分级**，并标注哪些结论需要二次核对。

## 一、本次分析采用的三层验证法

为避免单一工具误判，我对每个关键结论都尽量用三种方式交叉验证：

| 层级 | 方法 | 可靠性 |
|---|---|---|
| ① 原始字符串 | `strings`（ASCII + Unicode） | 极高（二进制直接提取，无歧义） |
| ② PE 结构 | `objdump -p`（导入表/导出表/节区） | 极高（结构事实） |
| ③ 反编译 | Ghidra `analyzeHeadless` + Decompiler | 中（可能有函数边界/调用约定误判） |

## 二、本次结论的可靠性分级

### 高可靠（strings/objdump 直接证据，不依赖反编译）

- ✅ 端口配置项名称：`ChannleScanPort`、`ConnectPort`、`MultiCastPort` 等
- ✅ 指令集：`Enable NetWork`、`Disable NetWork`、`Enable DUOC` 等（DeviceControl 字符串）
- ✅ MMPC 指令 type：`set-teaAndStu-ip`、`regedit-broadcast`、`start-multiclient` 等
- ✅ 关机命令：`shutdown.exe -f -s -t 0`、`shutdown.exe -f -r -t 0`（MmcImplBase 字符串）
- ✅ 远程 cmd：`cmd.exe`、`ShellExecuteW`、`/c taskkill /F /IM %s`
- ✅ JSON 模板：`{"method":"multimedia","args":{"teacher_ip":...`
- ✅ 驱动机制：KbFilter 的 IOCTL 常量、OeNetLimit 的 WFP、easyusbflt 的白名单
- ✅ 导出函数：`SYS_Shutdown`、`SYS_RunCommand`、`OE_SystemOff`、`OE_KillProcess` 等
- ✅ 加密痕迹：`SSLKEYLOGFILE`、`sslkey.log`、`BCryptOpenAlgorithmProvider`、CryptoPP 特征

### 中可靠（反编译推断，逻辑清晰但需注意细节）

- 🟡 `OE_SystemOff` 的 ExitWindowsEx 主路径 + shutdown.exe 兜底逻辑（参数映射明确）
- 🟡 `SYS_Shutdown` 的 case 1/2/3/4 对应 关机/重启/注销/锁屏
- 🟡 `SYS_RunCommand` 的 `/k` + ShellExecuteW 逻辑
- 🟡 teacherip JSON 构造顺序（FUN_1005ae30）
- 🟡 频道注册流程（FUN_10067fc0，HTTP channel_register）

### 需重点核对（Ghidra 反编译易出错处）

- 🟠 **checksum 算法**（FUN_1004c380）：反编译结果逻辑清晰，但 `rand() & 0x80000003` 的符号位处理需对照反汇编确认（IDA 可能给出更干净的 `rand()%4`）
- 🟠 **函数边界**：某些大型函数（如 DeviceControl 的 FUN_140021bd0）Ghidra 可能错误切分，需对照 IDA
- 🟠 **调用约定**：`__thiscall` vs `__fastcall` vs `__cdecl` 的识别，Ghidra 与 IDA 可能有差异
- 🟠 **IP 校验结论**：目前基于"未发现校验代码"的否定性结论，需动态实测确认

## 三、关于 Ghidra 与 IDA 冲突的说明

1. **Ghidra 反编译器的已知局限**：
   - 函数边界识别（`Function Start Search`）在无符号的 MFC/C++ 程序上易出错；
   - x86 调用约定推断（thiscall/fastcall）可能误判；
   - 某些花指令/混淆会导致反编译失败或错误。

2. **本次规避措施**：
   - 关键结论**优先依赖 strings 直接证据**，而非反编译；
   - 端口、指令、命令等**字符串层面的结论**不受反编译影响；
   - 函数逻辑结论已标注"中可靠"，建议用 IDA 二次核对。

3. **若你有 IDA 的具体冲突点**，请告知具体函数/地址，我可针对性用 Ghidra 反汇编（非反编译）逐指令核对。
