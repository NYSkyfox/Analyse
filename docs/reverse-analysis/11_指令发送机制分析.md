# 11 指令发送机制分析（一次性 vs 循环）

> 本报告专门回答：**教师端的管控指令是"只发一次"还是"每隔一段时间循环重发"？**
> 方法：**反汇编调用图分析**（`MainLogic.dll`）+ **真实教师端抓包实证**（见 [12 报告](./12_教师端真实抓包实证.md)）。
> 结论：管控指令（cmdType=500）为 **事件驱动、只发一次**；教师端周期性发送的是 **7777 教师身份广播（每 3 秒）**，**不是管控指令**。

---

## 〇、结论速览

| 问题 | 结论 | 证据 |
|---|---|---|
| 管控指令 cmdType=500 是否循环发送？ | ❌ **不循环，只发一次** | `FUN_10067f50` 调用图 + 抓包（未连学生 8040 零流量） |
| 教师端是否有周期性发包？ | ✅ 有，但发的是 **7777 身份广播** | 抓包：`7777→7777` 每 3 秒一次 |
| 解除管控后会被"打回"吗？ | ❌ 不会（教师端不会周期重发管控） | 抓包 + 反汇编 |
| 什么时候会被重新管控？ | 教师端**再次点击"应用"** 时 | `Limit` 导出函数仅在用户操作时触发 |

## 一、发送链路调用图（反汇编实证）

### 1.1 `FUN_10067f50`（触发发送）的调用者只有 2 个

用 Ghidra 脚本 `FindCallers2.java` 遍历引用，得到：

```
FUN_10067f50 (组包+发送触发)
  ├─ Limit  @0x100197e0        ← ★ 导出函数（教师端点"确定/应用"时调用）
  └─ FUN_10077970 (UnLoad)     ← 程序退出时调用（发 CtrlCode=-0x44000000）
```

**关键点**：没有任何定时器/循环调用 `FUN_10067f50`。

### 1.2 `Limit` 导出函数体（完整，无循环）

```c
void Limit(void)
{
  FUN_10067f50(&DAT_1018faa0);   // 直接组包发送，无 while/timer
  ...
}
```

→ `Limit` 是**导出的外部接口**，由 UI 层（Teacher.exe 的"应用管控"按钮）**一次性调用**。

### 1.3 所有 `SetTimer` 都在初始化函数里（只执行一次）

Ghidra 脚本 `FindTimer.java` 扫描 `SetTimer` 引用，全部集中在 `FUN_10064990`：

```
SetTimer 符号 @EXTERNAL:00000060
  被引用位置（全部在 FUN_10064990 内）：
    from 10064c47   (timer id 1，周期 10ms)
    from 10064c61   (timer id 2，周期 10ms)
    from 10064c7b   (timer id 4，周期 3000ms)  ← ★ 每 3 秒
    from 10064c98   (...)
    from 10064e12 / 10064d7d / 10064e9d / 10064eba
```

`FUN_10064990` 是 **`MainLogic.dll` 的一个初始化函数**（`DllMain` 后的显式 Init），**进程生命周期内只调用一次**。

### 1.4 定时器回调 → 分发到 `FUN_10067fc0`，**不是** `FUN_10067f50`

```c
// 定时器回调（所有 SetTimer 共用）
void FUN_100773b0(param_1, param_2, param_3)
{
  if (DAT_10190180 != (void *)0x0) {
    FUN_10067fc0(DAT_10190180, param_3);   // ← 定时器走这里
  }
}
```

| 函数 | 用途 | 是否发管控 |
|---|---|---|
| `FUN_10067fc0` | 定时器回调入口（**频道注册/状态维护/HTTP 心跳**） | ❌ 不发管控 |
| `FUN_10067f50` | 管控组包发送（**仅 `Limit`/`UnLoad` 调用**） | ✅ 发管控 |

由此可判定：**3 秒定时器负责的是"教师身份广播/频道心跳"，与管控指令无关。**

## 二、抓包实证（决定性）

> 完整分析见 [12 报告](./12_教师端真实抓包实证.md)。此处摘录与"发送机制"直接相关的部分。

### 2.1 实验条件

- 教师机 `192.168.5.18`，教师端已打开并点击若干功能
- **未连接任何学生端**
- 抓包时长约 348 秒

### 2.2 结果：8040 端口出现 **0 次**

```
=== UDP 目标端口分布 ===
  dst 7771   x2903    ← 频道扫描（每 ~0.11s，组播 229.9.5.18）
  dst 7777   x105     ← ★ 教师身份广播（每 3s，全网广播）
  dst 7778   x90      ← 屏幕广播（组播 229.1.5.18）
  dst 12476  x70      ← 美的空调 IoT（无关）
  dst 15683  x6       ← 少量

8040 出现次数: 0
```

→ **未连学生时，管控通道（8040）上一条包都没有**，证明管控指令**不是周期性发送**。

### 2.3 周期性发送的到底是什么？

`7777 → 255.255.255.255:7777`，**每 3 秒一次**，载荷（UTF-8 明文 JSON，无前缀）：

```json
{
   "channel" : 4,
   "checksum" : 54503,
   "msg_id" : "teacherip",
   "teacher_ip" : "192.168.5.18"
}
```

- `msg_id = "teacherip"` → **教师身份公告**，不是管控
- `checksum` 每帧随机变化（54503→236367→470705→…），符合 [07 报告](./07_建议点深挖.md) 的 6 位随机算法
- `channel = 4` → 频道号（教师端可配置）

## 三、运行时序图

```
教师端启动
  └─ FUN_10064990（初始化，执行一次）
        └─ SetTimer(id=4, 3000ms, FUN_100773b0)   ┐
                                                    │ 每 3 秒
        ┌───────────────────────────────────────────┘
        ▼
   FUN_100773b0 → FUN_10067fc0  → 广播 7777{"msg_id":"teacherip",...}   （身份公告，非管控）

用户点击"应用管控"
  └─ Teacher.exe 读 NPDControl.json → 算 CtrlCode
        └─ 调 MainLogic 导出 Limit()
              └─ FUN_10067f50 → 组包 [500][0][0][len]+JSON → 遍历在线学生，逐台单播 8040   （★ 只发一次）

用户点击"停止管控" / 程序退出
  └─ UnLoad() → FUN_10077970 → CtrlCode=-0x44000000 → FUN_10067f50   （★ 只发一次）
```

**关键观察**：管控发送（`FUN_10067f50`）与定时器（`FUN_100773b0`）是**两条完全独立的链路**，互不调用。

## 四、对"注入工具"的直接指导

### 4.1 回答用户的两个假设

| 假设 | 判定 |
|---|---|
| ① 教师端只发一次，发"解除指令"后即解除 | ✅ **正确** |
| ② 教师端循环发送，解除后会被"打回" | ❌ **不成立**（教师端不循环发管控） |

### 4.2 解除管控的正确做法

```python
# 方案 A（推荐，UnLoad 语义 = 清除全部管控）
build_ctrl(-0x44000000, target_ip)

# 方案 B（兜底，空管控）
build_ctrl(0, target_ip)
```

> ⚠️ 建议**先发 A、再发 B** 双保险（详见 [10 报告 §七](./10_行为管控报文核查定稿.md)）。

### 4.3 ⚠️ 唯一的"打回"风险（需实测确认）

虽然管控指令**不循环**，但教师端**每 3 秒广播 `teacherip`**。存在一种可能：

> 学生端收到教师广播 → 刷新"教师在线"状态 → **主动向教师端请求当前管控策略** → 被重新管控。

这**取决于学生端逻辑**（是否在收到教师广播后主动拉取策略）。验证方法：

1. 在 B 上注入解除指令
2. **保持观察 ≥ 30 秒**
3. 同时抓 B 的流量，看 B 是否向教师端发起 8040 / 9003 请求

- 若 B **不主动请求** → 解除后稳定，不会被"打回"
- 若 B **主动请求** → 需要在解除后**阻挡/持续压制**该请求，或让 B 认为"教师不在线"

## 六、★★ 重大补充（2026-09-12）：存在"新学生上线补发"机制

> 用户实证：**"学生端在教师端发放管控指令 / 启动屏幕广播之后才连上教师端，学生端仍然会被控制。"**
>
> 这条实证**推翻了"只发一次"的简单结论**——存在**状态补发机制**。经反汇编重新追查，机制已完全还原。

### 6.1 核心机制：预命令缓存 + 上线补发

`MainLogic.dll` 中找到了 **`SendToNewStudentPreCommand`**（**向新学生发送预命令**）逻辑，日志字符串：

```
[MainLogic][SendToNewStudentPreCommand][xsys1][ip:%s][id:%d][type:%d]   @VA 0x10150830
[MainLogic][SendToNewStudentPreCommand][xsys0][ips:%s][id:%d][type:%d]  @VA 0x101508a0
[MainLogic][SendToNewStudentPreCommand][ykzb][ips:%s][id:%d][type:%d]   @VA 0x10150930
```

反汇编对应函数（VA `0x1006f400` 附近）确认：它在**新学生上线时被触发**，组包并**遍历在线学生列表**发送。

### 6.2 补发的报文（反汇编实证）

```asm
; === 分支 xsys1：补发管控类指令 ===
1006f864  MOV [EBP-0x3e8], 0x13    ; ★ cmdType = 0x13 = 19
1006f86e  MOV [EBP-0x3e4], 0x0     ; flag1 = 0
1006f875  MOV [EBP-0x3e0], 0x2     ; flag2 = 2
...
1006f9a5  CALL 0x1003f850          ; 写 16B 头 [19][0][2][len]
1006f9bc  CALL 0x10099650          ; 追加载荷
1006fa13  CALL 0x1009e070          ; ★ 遍历在线学生列表，逐台发送
```

> 💡 **`cmdType = 0x13 = 19 = 0x01|0x02|0x10`** —— 正好是 CtrlCode 的 `禁用网络(0x01) + 键盘过滤(0x02) + 禁用应用(0x10)` 组合。**这就是"补发的管控指令"！**

另有分支（VA `0x1006ee22` 附近）：

```asm
1006ee22  MOV [EBP-0xb0], 0x19     ; cmdType = 0x19 = 25
1006ee9d  CALL 0x1003f850          ; 写头
1006eee5  CALL 0x1009e070          ; ★ 遍历在线学生发送
1006eeea  PUSH 0x3e8               ; 1000ms
1006eeef  CALL 0x100990c0          ; Sleep(1000) —— 逐台之间间隔 1 秒
```

### 6.3 触发时机：学生上线事件

`MainLogic.dll` 导出了三个"学生上线"相关 API（供 `Teacher.exe` 动态调用）：

| 导出函数 | 调用链 | 发送的 cmdType |
|---|---|---|
| `SendCallSignToNewStudent` @0x10019a40 | → `FUN_1006c010` → `FUN_1009e070` | 0x0b(11) |
| `SendStudentParaConfig` @0x10019b40 | → `FUN_1006e160` → `FUN_1009e070` | 0x1c(28) |
| `UpdataStudentSign` @0x10019e00 | → `FUN_10077e40` → `FUN_1009e070` | 0x42(66) |
| **（内部）`SendToNewStudentPreCommand`** | `0x1006f400` → `FUN_1009e070` | **0x13(19) ← 管控** |

**`Teacher.exe` 通过 `GetProcAddress` 动态调用**（`Teacher.exe` 内不含这些字符串），当**检测到新学生上线**时调用。

### 6.4 修正后的完整时序图

```
教师端启动
  ├─ FUN_10064990（初始化）
  │     └─ SetTimer(3s) → 7777 身份广播（非管控）
  │
  ├─ 用户点"应用管控"
  │     └─ Limit() → FUN_10067f50 → [500][0][0][len]+JSON → 遍历在线学生 8040（★ 此刻在线者才收到）
  │
  └─ 新学生 X 上线（★ 关键！）
        └─ Teacher.exe 检测到 → 调 MainLogic 导出
              ├─ SendCallSignToNewStudent → [11]
              ├─ SendStudentParaConfig    → [28]
              ├─ UpdataStudentSign        → [66]
              └─ SendToNewStudentPreCommand → [19 = 管控!] （★ 补发管控给 X）
```

### 6.5 结论修正（重要）

| 原结论 | 修正后 |
|---|---|
| 管控"只发一次" | ⚠️ **不准确**。是"**首次应用时发一次 + 每个新学生上线时补发一次**" |
| 后连接学生不受控 | ❌ **错误**。后连接学生会被**补发管控**（用户实证 + 反汇编双证） |
| 教师端不重发管控 | ✅ **仍成立**（教师端不对**已在线的**学生周期重发；重发只针对**新上线**的学生） |

### 6.6 对工具开发的致命影响 ⚠️

**你之前设想的"发一次解除指令即可永久解除"——在有教师端在线的情况下会失败**：

```
时间线：
  T1  你用工具向 B 注入"解除管控"
  T2  B 重新上线/重连教师端（或教师端刷新在线列表）
  T3  教师端检测到 B"新上线" → 补发 cmdType=19 管控  ← 你的解除被覆盖！
  T4  B 重新被管控
```

**因此工具必须处理"补发"问题，可选策略：**

| 策略 | 做法 | 优缺点 |
|---|---|---|
| **A. 持续压制** | 周期性（如每 1 秒）向 B 发解除指令，覆盖教师端补发 | 简单粗暴，但网络流量大、可能被发现 |
| **B. 阻断补发** | 在 B 上阻断教师端→B 的 19/25 报文（防火墙/驱动） | 彻底，但需在 B 上执行 |
| **C. 冒充教师** | 伪造 7777 广播 + 响应 B 的上线请求，让 B 认为"教师无管控" | 隐蔽，但需完整复刻状态机 |
| **D. 抢占上线时刻** | 监控 B 的上线，在其被补发后立即再发解除 | 需实时监控 |

**推荐组合：B（阻断）+ A（兜底）**。
