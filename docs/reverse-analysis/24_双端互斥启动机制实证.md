# 24 · 双端互斥启动机制实证

> 对象：`Teacher.exe` / `Student.exe`（极域多媒体电子教室 OSeasy）
> 方法：Ghidra 12.1.3 全量反编译 + 原始 PE 二进制 UTF-16LE/ASCII 字符串扫描 + 启动链反编译
> 结论级别：命名内核对象（Named Event）互斥，**两端代码对称，全部静态实锤**

---

## 1. 现象

同一台机器上，教师端与教师端、学生端与学生端、教师端与学生端，**后启动的一方在启动阶段弹出提示框**。提示框为 DuiLib 模态对话框，含一个主按钮，按钮旁带 **5 秒倒计时**，倒计时归零后对话框自动关闭，进程随之退出，不进入主界面。

本文仅陈述该机制的静态判定逻辑与证据，不涉及其它功能。

---

## 2. 判定原语：命名事件存在性检测

两端均使用同一种检测原语——以名称 `OpenEventW` 探测命名事件是否存在。

### Student.exe（反编译可定位）

`FUN_004bb0b0`（Ghidra 工程 `studentexe`，反编译存档 `studentexe_x86.txt` line 136072）：

```c
bool __fastcall FUN_004bb0b0(undefined4 param_1)
{
  LPCWSTR lpName;
  HANDLE  pvVar1;
  lpName = (LPCWSTR)FUN_004093e0(param_1);   // 取事件名
  pvVar1 = OpenEventW(0x1f0003, 0, lpName);   // EVENT_ALL_ACCESS, 不创建
  return pvVar1 != (HANDLE)0x0;               // 句柄非空 = 事件已存在
}
```

`0x1f0003 = EVENT_MODIFY_STATE | EVENT_ALL_ACCESS`。`OpenEventW` 不带创建语义，事件已存在则返回句柄，否则返回 `NULL`。返回值 `1` 表示该命名事件当前**已被某进程创建**，`0` 表示不存在。

事件名由 `FUN_004084a0(name)` 在调用前设定，`FUN_004bb0b0()` 随后读取该名称并 `OpenEventW`。

## 3. 启动检查链（Student.exe `WinMain` 入口 `FUN_004bcc60`）

`FUN_004bcc60`（`studentexe_x86.txt` line 137727 起）在完成 DuiLib 资源路径设置后，进入互斥检查。逻辑还原如下：

```c
// ① 检测 TeacherEvent
FUN_004084a0(L"TeacherEvent");
bool teacherExists = FUN_004bb0b0();          // OpenEventW("TeacherEvent")
if (teacherExists == 0) {
    // ② TeacherEvent 不存在 → 检测 StudentEvent
    FUN_004084a0(L"StudentEvent");
    bool studentExists = FUN_004bb0b0();      // OpenEventW("StudentEvent")
    if (studentExists == 0) {
        // ③ 两个事件都不存在 → 正常启动主窗口
        //    设置回调 DAT_005f01a8 = FUN_004bba40（退出时清理 StudentEvent）
        CreateDuiWindow(L"UIStudentMainWnd");
        MessageLoop();
    } else {
        // ④ StudentEvent 已存在（已有学生端在跑）→ 弹 StudentWarning
        //    主按钮 = "StudentRunning"，5 秒倒计时
        MessageBoxCreate(L"StudentWarning");
        setButton(L"StudentRunning");          // FUN_00403dd0("StudentRunning")
        ShowModal();
        FUN_0040f140();                          // 倒计时收尾 / 退出
    }
} else {
    // ⑤ TeacherEvent 已存在（已有教师端在跑）→ 弹 StudentWarning
    //    主按钮 = "TurnOffTeacher"，5 秒倒计时
    MessageBoxCreate(L"StudentWarning");
    setButton(L"TurnOffTeacher");               // FUN_00403dd0("TurnOffTeacher")
    ShowModal();
    FUN_0040f140();
}
```

### 5 秒倒计时

两个弹窗分支均出现相同的构造序列（`studentexe_x86.txt` line ~138540 / ~138600）：

```c
pwStack_1ac0 = L"StudentWarning";
```

`uStack_1acc = 5` 即用户观察到的「按钮旁 5 秒倒计时」。对话框为 DuiLib `CMessageBoxDlg`，布局来自 `skin/CommMessageBox.xml`。

## 6. 互斥判定逻辑（伪代码，两端通用）

设本端角色为 `SELF ∈ {Teacher, Student}`，对端为 `OTHER`：

```
teacherExists = OpenEventW("TeacherEvent") != NULL
studentExists = OpenEventW("StudentEvent") != NULL

if SELF == Student:
    if teacherExists:            # 已有教师端在跑
        ShowWarning("StudentWarning", button="TurnOffTeacher",  countdown=5); exit
    elif studentExists:          # 已有学生端在跑
        ShowWarning("StudentWarning", button="StudentRunning",  countdown=5); exit
    else:
        CreateEvent("StudentEvent")   # 登记自身
        LaunchMainWindow("UIStudentMainWnd")
else:  # SELF == Teacher
    if studentExists:            # 已有学生端在跑
        ShowWarning("TeacherWarning", button="TurnOffStudent",  countdown=5); exit
    elif teacherExists:          # 已有教师端在跑
        ShowWarning("TeacherWarning", button=(镜像),             countdown=5); exit
    else:
        CreateEvent("TeacherEvent")   # 登记自身
        LaunchMainWindow(...)
```

互斥由**命名事件**承载：某端启动并成功进入主界面时会 `CreateEventW` 一个带名字的事件（`TeacherEvent` 或 `StudentEvent`），进程存活期间该事件保持存在；正常退出时 `CloseHandle`/`FUN_004bba40` 释放。其它端启动时 `OpenEventW` 探测该事件，存在即判冲突。

> 事件由系统命名空间承载，跨进程可见，生命周期绑定创建进程（进程退出后内核自动回收事件对象）。这解释了为何无需额外的注册表/文件锁/端口探测。

## 8. 同时启动两端的可行路径

互斥完全依赖「命名事件是否已存在」这一单一判据。据此，同时启动两端的思路按侵入性从低到高：

1. **绕过检测（补丁）**：把两端启动检查里 `OpenEventW(...)` 的返回值强制为 0（即"事件不存在"），两端都会走"正常启动"分支并各自 `CreateEvent` 自己的事件。由于两端创建的是**不同名**的事件，彼此不冲突。最小改动是 patch 掉 `FUN_004bb0b0`（Student 端，`studentexe` @`0x4bb0b0`）使其恒返回 0；Teacher 端对应函数同理（其函数体在 Ghidra dump 中未完整覆盖，需用 `OpenEventW` 的 `OpenEventW` import 交叉引用定位）。
2. **运行期抢占**：在两端都启动前，预先用外部进程 `CreateEventW` 创建出"对端"的事件名是**反向**操作（会让本端误判冲突）；正确做法是确保检测点返回"不存在"。因此纯外部手段不如 patch 直接。
3. **双目录双角色**：与命名事件无直接关系，但可配合——两个安装目录各自独立，但**命名事件是全机命名空间共享的**，仅改目录/改 `TeaSide.ini` 的 `Flag` **不能**绕过互斥，因为 `OpenEventW("TeacherEvent")` 仍能探测到另一目录进程创建的事件。故方案 1（patch 检测点）是同时启动的必要条件。

> 结论：同时启动两端的**充分且最小**改动，是使两端启动检查的 `OpenEventW` 探测恒判"不存在"（patch `FUN_004bb0b0` 等检测原语）。命名事件本身按角色分名，patch 检测后两端可并存。

## 9. 备注

1. **定位方法的坑（已纠正）**：早期对 Ghidra 反编译存档 `teachexe_x86.txt` grep `TeacherEvent`/`StudentEvent` 文本 0 命中，一度误判为"不对称 / 函数未 dump"。**真正原因**：反编译里事件名是**经 `FUN_004181e0` 作为参数传入** `OpenEventW` 的（运行时取出的字符串），不以字面量 `L"TeacherEvent"` 形式出现在反编译文本中，故 grep 文本落空。**正确定位方式**是 grep 检测原语 `OpenEventW`（`teachexe_x86.txt` line 302634），其所在函数即 `FUN_005b9420`（line 302627）。原始 PE 二进制里这两个事件名确实是明文 UTF-16LE（Teacher.exe 文件偏移 `0x2c98d0`/`0x2c992c`/`0x2c9834`），与反编译文本形式不同。
2. **Teacher.exe 是 x86-32**（machine `0x14c`）：无 RIP 相对寻址，字符串引用经绝对地址 / `.data` 指针间接完成，纯字节扫描字符串 VA 不可靠；机制判定以 **Ghidra 反编译函数体** 为准。
3. **事件名明文**：`TeacherEvent`/`StudentEvent` 在两端二进制中均为明文（UTF-16LE），与弹窗正文（运行时解密的乱码宽串）不同，对**原始 PE** 静态可直接命中；但在反编译 dump 中不出现为文本字面量。
4. `LocalSystem.oseasy`（Teacher.exe `0x2b8b20`）为另一处 `FindWindowW` 目标（窗口类/标题探测，配 `SendMessageW 0x4a` 传路径），与本互斥机制无关，属独立的功能窗口探测。
