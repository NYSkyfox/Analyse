# 15 · 学生端"在线 / 掉线"判定机制（WebSocket 空闲超时）

> 本文分析 Os-Easy 教学系统中「学生端进程挂起」与「学生端进程结束」两种情况下，教师端在线状态判定差异的原因。
>
> 数据来源：样本静态分析（字符串表 / 符号表 / 配置文件）+ 现场观测现象
> 涉及文件：`Teacher.exe`、`MainLogic.dll`、`StudentLogic.dll`、`skin/core.conf`

---

## 一、观测到的现象

| 操作 | 教师端显示 | 学生端画面 |
|---|---|---|
| **挂起**学生端进程（Suspend） | **仍显示在线** | **定格**（不再更新） |
| **结束**学生端进程（Kill） | **立即显示掉线** | — |

即：进程被冻结时教师端不认为其离线；进程被销毁时教师端立即认为其离线。

---

## 二、逆向证据

### 2.1 连接协议为 Boost.Beast WebSocket

在 `MainLogic.dll`（教师端）与 `StudentLogic.dll`（学生端）的符号表中均存在：

```
boost::beast::websocket::stream<...>
boost::beast::websocket::detail::idle_ping_op<...>      ← 空闲 Ping 实现
boost::beast::async_read / read_op / accept_op
```

→ 学生端与教师端之间的长连接为 **WebSocket**（基于 Boost.Beast 实现），而非裸 TCP 自定义协议。

### 2.2 存在超时关闭路径

| 字符串 | 所在文件 |
|---|---|
| `The socket was closed due to a timeout` | MainLogic.dll / StudentLogic.dll |
| `[%d] websocket read error:%s` | MainLogic.dll / StudentLogic.dll |
| `[%d] client websocket disconnect!` | StudentLogic.dll |
| `[%d]disconnect` | MainLogic.dll |
| `%s Desktop disconnect` / `%s Terminal disconnect` | MainLogic.dll |
| `SOCKET_ERROR` | MainLogic.dll |

### 2.3 断开后更新界面状态

| 字符串 | 所在文件 |
|---|---|
| `Offline` / `OfflineBak` / `stuOffline` / `stuRemoveOffline` | Teacher.exe |
| `DisconnectMulti` | Teacher.exe |

### 2.4 配置中无超时项

- `skin/core.conf` 中**不存在** timeout / idle / keep-alive 相关配置项；
- 因此超时参数**取库默认值**（Boost.Beast `stream_base::timeout` 默认 `idle_timeout = 300 秒`）。

---

## 三、机制还原

### 3.1 两种操作的对比

| 层面 | 挂起进程 | 结束进程 |
|---|---|---|
| 内核 socket | 保持存在 | 被内核回收 |
| TCP 连接 | 保持 ESTABLISHED | 发送 **FIN**（正常退出）或 **RST**（强杀） |
| WebSocket 帧 | **不再发送/回应任何帧** | 连接随即消失 |
| 教师端感知 | 读操作进入**空闲计时** | **立即**收到读错误（`websocket read error`）→ 触发 disconnect |
| 结果 | **短时间内判定"在线"**；约 **300 秒**后因空闲超时断开 → 掉线 | **立即**判定"掉线" |

### 3.2 结论

1. **在线判定依据 = WebSocket 连接的存活状态**，而**非应用层业务心跳超时**；
2. 杀进程会**立即**在 TCP 层产生 FIN/RST → 教师端立刻收到读错误 → 立即标记掉线；
3. 挂起进程时 TCP 连接仍由**内核**维持，但应用层停止响应 → 教师端要等到 **WebSocket 空闲超时（默认 300 秒）** 才会标记掉线；
4. 因此存在一段 **"假在线"窗口**（约 5 分钟），期间教师端显示在线、但画面停止更新。

> 注：`idle_ping_op` 符号的存在说明**构建中包含空闲 Ping 机制**；其是否启用（`keep_alive_pings`）与具体超时值需通过动态实验确认。

## 四、验证方法

| 步骤 | 操作 | 预期观测 |
|---|---|---|
| 1 | 挂起某台学生端进程，记录开始时间 | 教师端仍显示在线 |
| 2 | 持续观察教师端界面 | 在约 **300 秒**后变为"掉线"（若为其他数值，说明超时被修改） |
| 3 | 挂起期间抓包 | 可见 TCP ACK 往返，但**无任何 WebSocket 数据帧** |
| 4 | 超时断开瞬间抓包 | 出现 **FIN 或 RST** |
| 5 | 直接结束另一台学生端进程 | 教师端**立即**显示掉线 |

---

## 五、对工具开发的意义

1. **"挂起进程"不能长期伪装在线**：仅能维持约 5 分钟，之后仍会掉线；
2. **要长期伪装在线**：必须真正维持 WebSocket 连接并周期性回应（回 Pong / 发送数据），仅保持 TCP 连接不足够；
3. **若要隐蔽断开**：直接杀进程会**立即**触发教师端掉线告警，而挂起可争取约 5 分钟的时间窗口；
4. **管控命令的下发与响应均依赖该 WebSocket 连接**：连接断开即意味着管控通道失效。
