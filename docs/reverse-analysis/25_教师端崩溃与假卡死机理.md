# 25 · 教师端 9003 崩溃与"假卡死"机理（二次修正版）

> 本文基于 Ghidra x86 反编译 `mainlogic_x86.txt` / `teachexe_x86.txt` 逐字节复核，回答：教师端收到 9003 包后如何处理？崩溃工具的非法包为何让教师端崩溃？为何"假卡死"（学生全掉线、画面定格、不显示离线、只能重启）？
> 数据来源：Ghidra 反编译 + `Sample/captures_20260914/*.log` 现场抓包 + `tools/crash_old_gui.py` / `crash_new_gui.py` 载荷。
> **版本说明**：本版对 2026-10-23 初版做了**实质修正**（初版把 UDP 收包函数 `FUN_10099e30` 误当成 9003 TCP 收包，从而误判"9003 无重组层"）。修正依据见 §一/§二/§九。
> 分析日期：2026-10-23（二版）

## 〇、结论速览

1. **9003 是纯二进制长度前缀协议，不是 HTTP**。帧格式为 `[4B total_len][4B cmdType][4B u3][4B u4][4B body_len][payload]`，`total_len = 16 + body_len`。抓包心跳 `10000000 59000000 40000000 ...` 与该结构逐字节吻合。
2. **9003 存在严格的"读头 → 按头长度读体"拆帧状态机**：`FUN_1009bed0` 先 `async_read` 4 字节头 → `FUN_1009bcb0` 用头值经 `FUN_1009bb40` **扩容 body 缓冲** → 再 `async_read` body → `FUN_1009bb90` 校验后把**已剥掉长度头的 body** 入队。初版"无重组层"结论**错误，已废除**。
3. **旧版 `oshack\r\n` 的崩溃点在长度头上，不在 cmdType 分发里**：`"osha"` 小端 = `0x6168736F` = **1,633,262,447 字节 ≈ 1.52 GiB**。服务器把它当 body 长度去 `operator new`（`FUN_10135865` → `FUN_10135089`），32 位进程必然分配失败 → 异常/空指针 → 崩溃。
4. **新版双包**的 `pkt2` 长度头 `0x518` 合法（=16+0x508），走 `cmdType=0x2B` 的 JPEG 解码路径崩溃；与旧版**殊途同归**（都是攻击者可控长度/畸形内容 + 无防护），所以"效果几乎一样"。
5. **"第一包 10061、第二包成功"**：9003 服务器（`this+0x30`）不是在 `Load` 时同步创建，而是由 `FUN_100712d0` 作为**事件回调**创建（`FUN_1002fa20/fa80` 注册）。回调未触发的窗口内端口无监听 → 内核 RST → 10061。**该窗口的存在为反编译事实；"何时被触发"仍需动态验证**。
6. **"假卡死"**：崩的是 **asio IO/读完成回调线程**，不是 UI 线程。读线程死 → 无新画面帧、在线状态机不更新（不显示离线）；UI 线程存活（窗口可操作）；学生端用自己的线程检测到断链 → 学生掉线。

## 一、9003 服务器：谁创建、何时创建

### 1.1 初始化入口与对象布局

`MainLogic.dll` 的导出函数 `Load`（main@19810）→ `FUN_10064990(&DAT_1018faa0)`（main@98985）：

```

*(this+0x3c) = <栈参数>;                             main@99078          ← 服务器端口（外部传入）
FUN_1005e5e0(this);                                   main@99085          ← 读 core.conf
```

`FUN_1005e5e0`（main@94568）中坐实 9003 配置来源：

```

uVar2 = FUN_10002a50();
*(undefined2 *)(param_1 + 0x58) = uVar2;   main@94605   ← 端口存 this+0x58（2 字节）
```

### 1.2 服务器是"事件回调"创建的（关键）

```
FUN_1002fa20(this+0x18, FUN_100712d0);   main@99095
FUN_1002fa80(this+0x1c, FUN_100712d0);   main@99100
FUN_1002fa80(this+0x20, FUN_100712d0);   main@99105
```

`FUN_100712d0(param_1=端口, param_2)`（main@106511）按参数分三路建服务器：

| 分支 | 构造 | 创建函数 | 存入 |
|---|---|---|---|
| `param_1 == 0x232c` | `FUN_100408c0(..., 0x232c)` | `FUN_1009dac0(...,0,...)` | `this+0x38`（**9004**，硬编码） |
| `param_2 == 0` | `FUN_100408c0(..., (undefined2)param_1)` | `FUN_1009dac0(...,0,...)` | `this+0x30`（主服务器） |
| else | 同上 | `FUN_1009dac0(...,1,...)` | `this+0x34`（第二服务器） |

`FUN_1009dac0`（main@147654）→ `FUN_1009cbd0`（main@146761）是 asio acceptor 封装，逐行坐实：

```

FUN_1009d850(...,'\x01')   main@146806  ← set_option
FUN_1009f8d0(...)          main@146840  ← bind
```

> **推断**：这构成"存在未监听窗口"，解释第一次 10061。
> **未验证**：哪个事件、何时触发该回调（需动态下断 `FUN_100712d0` 观察）。初版把 10061 归因于"队列冷启动"，属错误解释。

## 二、真实收包与拆帧状态机（★本版核心修正）

9003 的每个连接使用**两段式异步读**，函数链如下（全部 mainlogic_x86.txt）：

```
FUN_1009bed0(this)                                   main@146027
  ├ FUN_1002fc00(..., FUN_1009bcb0, this, ...)       main@146036  ← 读完成回调 = 头
  ├ FUN_1007ef00(buf, this+0x4c, 4)                  main@146042  ← 缓冲 = &this+0x4c，长度 = 4
  └ FUN_1009a970(this, conn, buf, handler)           main@146048  ← async_read(4B)

FUN_1009bcb0（读头完成）                             main@145908
  ├ 出错 → 日志 "ReadedHeader error:%s"              main@145931
  │        → FUN_1009c1d0(this,'\0') 断连
  └ 成功 → FUN_1009bb40(this+0x50, *(size_t*)(this+0x4c))   main@145954
            └ 若容量 < 头长度：free(*this);
               *this = FUN_10135865(头长度);   ← ★ operator new(攻击者可控长度)
               this+4 = 头长度                main@145806-145815
           → FUN_1002fc00(..., FUN_1009bb90, this, ...)     main@145959  ← 读体完成回调
           → FUN_1007ef00(buf, 缓冲, *(uint*)(this+0x4c))   main@145966
           → async_read(body)

FUN_1009bb90（读体完成）                             main@145872
  ├ 出错 → 日志 "ReadedBody error:%s" → 断连
  └ 成功 → FUN_10008a00(..., this+0x58)              ← 取 body 字符串
           FUN_1009de60(*(this+0x74), buf, *(this+0x4c))  main@145883  ← 入队
           FUN_1009bed0(this)                        ← 继续读下一帧头

FUN_1009de60(this, data, len)                        main@147863
  └ 构造消息对象 → FUN_100a0610(this+0x54, obj)      main@147904  ← push 到连接队列
```

**结论**：入队的是**已经去掉 4 字节长度头的 body**，且每帧 body 长度由头字段决定。所以进入 `FUN_1005ed80` 的 `body[0]` 就是 `cmdType`，与 §三 帧格式自洽。

> 初版错在哪：把 `FUN_10099e30`（main@144032，`Ordinal_17` = `recvfrom`，socket 在 `this`）当成 9003 收包。该函数的真实用途见 §八：它是 **UDP 通道**的收包器，被 `FUN_10064340`（UDP 键鼠服务）和 `FUN_10067fc0` 的 `this+0x5ec` 分支调用，与 9003 的 TCP 帧无关。

## 三、帧格式（抓包 + 代码双向坐实）

现场抓包（`Sample/captures_20260914/192.168.1.7_big.log`）：

```
[34.355] TCP 192.168.1.200:9003 -> 192.168.1.7:49748 len=20
HEX: 1000000059000000400000000000000000000000
```

| 偏移 | 字节 | 值 | 含义 |
|---|---|---|---|
| 0x00 | `10 00 00 00` | 16 | total_len（body 长度） |
| 0x04 | `59 00 00 00` | 0x59 | cmdType = 心跳 |
| 0x08 | `40 00 00 00` | 0x40 | u3 |
| 0x0C | `00 00 00 00` | 0 | u4 |
| 0x10 | 4 字节 0 | 0 | body_len = 0，后接空 body |

发送端代码印证：`FUN_10067fc0` 的 `this+0x5e4`（timer id=3，5000ms）分支构造 `local_b4=0x59, local_b0=..., local_ac=0, local_a8=0`（16 字节），`FUN_1003f850` 追加进缓冲，`FUN_1009e070(this+0x30, buf, len)` 发送（main@101200-101220）。`FUN_1009e070` 在发送前补 4 字节长度头，故线上 0x59 位于偏移 4。

**新版 pkt2 自洽验证**：`18050000` = 0x518 = 1304 = 16 + 0x508，`body_len=0x508`，完全符合 `total_len = 16 + body_len`。

## 五、旧版 `oshack\r\n` 为何崩（★崩溃点重定位）

载荷 8 字节：`6f 73 68 61 63 6b 0d 0a`。

按 §三 协议，服务器**先读 4 字节长度头**：

```
长度头 = 6f 73 68 61 → 小端 0x6168736F = 1,633,262,447 字节（约 1.52 GiB）
```

随后 `FUN_1009bcb0` → `FUN_1009bb40`：

```c
if (*(int *)(this + 4) < param_1) {          // 已有容量 < 1.52GiB
    free(*(void **)this);
    *(undefined4 *)this = FUN_10135865(param_1);   // ← operator new(1.52GiB)
    *(size_t *)(this + 4) = param_1;
}
```

- `FUN_10135865` → `FUN_10135089`（main@285148，CRT 分配器）。MainLogic.dll 为 **32 位 x86**，单块 1.52 GiB 连续虚拟内存几乎必然失败。
- 失败后：`operator new` 抛 `std::bad_alloc`（在 asio 读完成回调栈中未被捕获 → `std::terminate`），或返回空指针后被 `async_read` 使用 → **访问违例**。
- 结果：连接被内核 RST（无 FIN）→ 客户端收 `WSAECONNRESET(10054)`；承载该连接的 IO 线程停止服务 → 后续帧不再处理。

> 所以旧版的崩溃**发生在长度头**，连 `cmdType` 分发都还没进入。这解释了为什么"纯字节也崩、与 JPEG 无关"，也解释了为什么 8 字节包若恰好被路由到 else 空出口——**根本没有 else 分支可走**，因为崩在更前面。
> 初版"单包落入空 else 所以不崩"的推理，前提（无拆帧层）已被推翻，结论一并作废。

**为什么第二次才成功**：见 §七。

## 六、新版双包为何崩

`pkt2`（`DEFAULT_PKT2`）：

```
18 05 00 00   total_len = 0x518（合法，=16+0x508）
2b 00 00 00   cmdType   = 0x2B（学生上报屏幕）
40 00 00 00   u3        = 0x40
00 00 00 00   u4        = 0
08 05 00 00   body_len  = 0x508 (1288)
ff d8 ff e0 ...  JFIF 头 + DQT + 全 0xFF 垃圾
```

- 长度头合法 → 正常读完 body → `cmdType=0x2B` 命中 main@95217 → `FUN_10030b40`（main@48493）→ `FUN_10056560` → **Teacher.exe** 的 JPEG 解码 `FUN_0040a6a0`（teachexe@8619）：`jpeg_std_error`(8712) → `jpeg_read_header`(8732) → `jpeg_start_decompress`(8762) → `jpeg_read_scanlines`(8809)。
- DQT 之后全为 `0xFF`：解码器对异常 marker/尺寸的缓冲分配与 `memcpy`（teachexe@8840）越界 → 崩溃。
- 路径与旧版不同（旧版崩在长度头分配），但结果一致：连接 RST → 10054，IO 线程停摆 → 假卡死。

> 用户观察"关键不在假 jpg，旧版纯字节也崩"——**成立**：两条路径都成立，但触发点不同。这是本版相对初版的重要修正。

## 七、为何"第一包 10061、第二包基本成功"

**事实**：9003 服务器对象由事件回调 `FUN_100712d0` 创建（§1.2），`Load` 阶段仅注册回调并清零 `this+0x30/0x34/0x38`。

**推断**：回调未触发的窗口内，9003 无监听者 → 内核直接 RST → `WSAECONNREFUSED(10061)`；回调触发后再连即成功。

**未验证**：
- 触发该回调的具体事件（UI 操作 / 定时器 / 首次连接"敲门"）；
- 触发延迟是否约等于现场观察的"约 10 秒"；
- 是否每次进程启动都必然出现一次未监听窗口。

**下一步（精确）**：WinDbg 下断 `FUN_100712d0`（RVA 0x100712d0），首次连接前后各观察一次命中与 `param_1`（端口）实值；同时 `netstat -ano | findstr :9003` 记录监听出现时刻。

## 八、`FUN_10099e30` 的真实身份（初版错误的根源）

```
FUN_10099e30(this, out)   main@144032
  iVar1 = Ordinal_18();
  if (iVar1 < 1 || Ordinal_151() == 0) { ... }
  else {
    memset(local_1014, 0, 0x1000);          ← 4KB 缓冲
    FUN_10008b40(...,"IpProto"); ...
    uStack_11ac = *(undefined4 *)this;      ← socket 句柄
    Ordinal_17();                            ← recvfrom
    FUN_1000b920(this+4, local_1014);       ← string::assign
  }
```

- `Ordinal_17` 的入参形态（socket / buf / 0x1000 / 地址结构）与 `recvfrom` 一致；`FUN_1009a170`（main@144108）则是同一族的 **UDP bind**（`Ordinal_23(2=AF_INET,2=SOCK_DGRAM,...)` + `Ordinal_21(...,0xffff)` + `inet_pton` + `Ordinal_2`=bind）。
- 调用者：
  - `FUN_10064340`（main@98660，UDP 键鼠服务）：`vender_id=="oseasy.mmc.udp"`、`id=="mouse"/"keybroad"` → `FUN_10072160`/`FUN_10072100` 注入键鼠；
  - `FUN_10067fc0` 的 `this+0x5ec`（定时器）分支：`FUN_10099e30(this+0x4c8, ...)` → `FUN_10066590()`。
- 因此这是 **UDP 通道**（对应 `UdpMessageControllerPort` 等），与 9003 的 TCP 帧流无关。初版据此推导的"无重组层"不成立。

## 九、为何"假卡死"

```
Teacher.exe 进程（加载 MainLogic.dll）
├── UI 线程（Qt5/Win32）                  ← 存活：窗口可操作
└── asio IO/读完成回调线程                 ← ★ 崩溃/停摆
      ├── FUN_1009bed0 → FUN_1009bcb0 → FUN_1009bb90（9003 拆帧）
      ├── FUN_1009de60 → 队列 → FUN_10067fc0（定时器消费）→ FUN_1005ed80
      ├── 0x2B → JPEG 解码 → Post 给 UI 刷新
      ├── 心跳/断线事件 → NodeManager m_nConnectsOnline（main@148967）
      └── "%s Desktop/Terminal disconnect"（main@95042/95076）
```

| 现象 | 原因 |
|---|---|
| 画面定格最后一帧 | 刷新依赖 IO 线程持续收 0x2B → 解码 → Post UI；线程停 → 无新帧 |
| 不显示学生离线 | 在线状态机由 IO 线程事件驱动；线程停 → 状态冻结 |
| UI 仍可操作 | 崩的是 IO 线程，非 UI 线程 |
| 学生端掉线 | 不对称：学生端用自己的线程检测（独立进程），收到 RST/超时即判定教师消失 |
| 必须重启 | asio 事件循环与连接/队列状态无自愈机制 |

> 本节为**推断**（与现象完全自洽，且线程归属有代码结构支撑），尚缺崩溃转储实证。
